## Compact Rules

### nextjs-15
- Server Components are the default — no directive needed
- "use client" ONLY for useState/useEffect/event handlers/browser APIs
- App Router: layout.tsx, page.tsx, loading.tsx, error.tsx at appropriate levels
- Data fetching: Promise.all for parallel, Suspense for streaming
- Server Actions: "use server" directive; revalidatePath/redirect for mutations
- Middleware at root middleware.ts with matcher config; no client-imports
- Use `import "server-only"` to prevent server code leaking to client bundles
- Static export (output: "export") disables server-side features

### react-19
- NEVER useMemo/useCallback — React Compiler auto-optimizes (React 18 forward-compat)
- ALWAYS named imports: `import { useState } from "react"` — never `import React`
- ref is a regular prop in React 19; no forwardRef wrapper needed
- use() hook reads promises (suspends) and context conditionally
- "use client" boundary: push it as deep as possible in the component tree

### tailwind-4
- NEVER put var() or hex colors in className — use Tailwind semantic classes
- cn() = clsx + tailwind-merge; use for conditional/conflicting classes only, NOT static
- Tailwind 4: NO tailwind.config.js; config via @theme in globals.css and PostCSS plugin
- Style constants with var() ONLY in style props for library components (Recharts etc.)
- This project: Tailwind 4.1.9 via @tailwindcss/postcss; config in postcss.config.mjs

### typescript
- Const types pattern: `const X = {...} as const` → `type X = (typeof X)[keyof typeof X]`
- Flat interfaces: one level deep; inline nested objects get dedicated interfaces
- NEVER `any` — use `unknown` + type guards (`value is Type`)
- Utility types: Pick, Omit, Partial, Required, Record, ReturnType, Parameters
- Project tsconfig: strict mode enabled, path alias `@/*` maps to root

### ui-ux-pro-max
- Color contrast: minimum 4.5:1 for normal text (CRITICAL)
- Touch targets: minimum 44x44px (CRITICAL)
- Focus states: visible focus rings on ALL interactive elements (CRITICAL)
- Animation: 150-300ms; use transform/opacity, not width/height; check prefers-reduced-motion
- Loading states: skeleton screens; disable buttons during async operations
- No emoji icons — use SVG icon libraries (lucide-react)
- Reserve space for async content to prevent cumulative layout shift

### branch-pr
- Every PR MUST link an approved issue (`Closes #N`, `Fixes #N`, `Resolves #N`)
- Branch naming: `type/description` — type ∈ {feat, fix, chore, docs, style, refactor, perf, test, build, ci, revert}
- Exactly one `type:*` label per PR
- Conventional commits: `type(scope): description`

### work-unit-commits
- Commit by deliverable work unit, NOT by file type (models → services → tests)
- Tests live in the same commit as the behavior they verify
- Docs live with the user-facing change they explain
- Each commit tells a story; future PR-ready
- >400 changed lines → group commits into chained PR slices

### chained-pr
- Split at 400 changed lines unless maintainer accepts `size:exception`
- Each PR reviewable in ≤60 minutes
- Include dependency diagram with 📍 in every chained PR body
- Don't mix chain strategies after choosing one (stacked-to-main vs feature-branch-chain)
- Feature Branch Chain: child #1 → tracker branch; later children → immediate parent

### cognitive-doc-design
- Lead with the answer/outcome; context comes AFTER
- Progressive disclosure: happy path first, then details, edge cases, references
- Prefer tables, checklists, examples, templates over dense prose
- State what to review first; state what's intentionally out of scope
- Link previous/next PR when chained

### comment-writer
- Start with the actionable point; don't recap before feedback
- 1-3 short paragraphs max
- Explain WHY when requesting changes (technical reason)
- Match thread language; Spanish → Rioplatense/voseo (`podés`, `fijate`, `dale`)
- No em dashes

### issue-creation
- Search duplicates first
- Use template: bug report OR feature request
- Fill ALL required fields before submitting
- Wait for maintainer `status:approved` before opening PR

### judgment-day
- Launch two blind judges in parallel; never review code yourself
- Classify warnings as real (normal use triggers) or theoretical → downgrade to INFO
- Only fix confirmed issues (both judges agree); re-judge after fixes
- Terminal states: `JUDGMENT: APPROVED` or `JUDGMENT: ESCALATED`
